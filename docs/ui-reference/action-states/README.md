# Naki UI Action-State Reference

This directory is the canonical visual reference for the proposed Naki interface.

## Scope

- Preserve the current Naki macOS toolbar and right-side decision-panel relationship.
- Use one consistent optimized sidebar and toolbar design.
- Produce one PNG per distinct user-visible recommendation behavior.
- Include the minimum non-action states needed to design empty, disabled, and failure paths.
- Treat the left Mahjong Soul WebView as an external surface; do not redraw it in the deterministic prototype.

## Source references

- `prototype.html`: canonical interactive HTML/SVG source of truth.
- `rendered/`: canonical browser-rendered PNG states.
- `tile-sprite.svg`: the 40 shipping tile assets merged into one sprite, generated by
  `scripts/build-tile-sprite.py`. Regenerate and re-inject with
  `python3 scripts/build-tile-sprite.py --inject` whenever the asset catalog changes.

## Decision log

### Deterministic HTML/SVG over additional generated raster images

Why: generated UI images drifted in Chinese copy, tile faces, proportions, and sidebar geometry. A single state-driven HTML file makes every label and layout rule reproducible and lets all states share one implementation. The superseded raster explorations were removed from this directory so there is only one visual authority.

Tradeoff: HTML/SVG is less atmospheric than image generation, and the discarded explorations are no longer available inside the repository. The remaining references are deterministic and materially easier to review and implement.

### Draw tiles from the shipping asset catalog, not hand-drawn SVG

Why: the prototype originally drew its own tiles (a digit plus 萬, a grid of circles, arrow-like
bamboo). Those were not the tiles the app renders, so the reference could not answer the one
question it exists to answer — is this tile legible at this size? The hand-drawn set also had no
way to express a red five.

The prototype now embeds the same FluffyStuff/riichi-mahjong-tiles assets the app ships
(`scripts/build-tile-sprite.py` merges them, namespacing each file's internal ids so the 40
Inkscape documents do not clobber each other's gradients). Tile faces are composited over
`Front.svg`, because this asset set separates the tile body from the face artwork.

Tradeoff: the prototype grew from 29KB to ~517KB. It remains a single self-contained file, which
is what makes the `.swfd` byte-identical mirror and the `下載 HTML` button work.

### Pass is not a tile

Why: `過` borrowed the red tile back as a placeholder. That asserted two things that are not
true — that the action involves some particular tile, and that it is dangerous (red is the danger
colour in this interface). It is now a neutral dashed empty slot, which reads as "deliberately no
tile here" rather than "tile failed to load". The concealed kan still uses real tile backs, where
the face-down meaning is correct.

### Do not redraw the Mahjong Soul game surface

Why: the left WebView is owned by the game, not Naki. Redrawing it spent effort outside the redesign boundary and introduced false details. The prototype now shows a neutral WebView placeholder and concentrates design work on Naki-owned chrome, the right decision panel, and the status bar.

Tradeoff: standalone screenshots look less like a finished game session, but they communicate the product boundary honestly and prevent the reference from specifying UI that Naki does not control.

### Button grid instead of a select menu

Why: comparing 17 closely related states is a repeated navigation task. Visible buttons reduce interaction cost, expose the full state space, and make the currently selected state obvious without opening a menu.

Tradeoff: the prototype control surface consumes more screen space. It is hidden in `capture=1` mode, so exported reference PNGs remain clean.

### The game/model row must expose real content

Why: a wireframe must demonstrate every visible control. The former row looked expandable but contained no panel, so it communicated a feature without specifying its behavior.

The row is now a functional disclosure. It shows round/honba/kyotaku, seat and four-player scores, dora indicator, model and decision source, local/cloud inference location, cloud state, and server-authorized action availability. The dedicated `details-open` state records the expanded appearance.

The summary strip *is* the disclosure. The sidebar previously carried two rows for one dataset —
a summary strip (`東 1 局｜自風 東｜25,000｜Mortal 4P`) and, far below it, a separate
`牌局與模型資訊` row that expanded the same information. Merging them costs no vertical space
when collapsed and puts the detail directly under its own summary when open.

Tradeoff: the panel expands inline and the `其他選項` list yields while it is open. Two earlier
versions were worse:

- *Absolute overlay.* The panel grew with its content, so it climbed over the probability bar and
  over its own summary row, leaving no visible affordance to collapse it again.
- *Inline, but anchored at the bottom of the sidebar.* Expanding inline forced an honest
  measurement the overlay had been hiding: the detail content overflowed the sidebar by 83px.
  Closing that gap cost tighter section padding and compressing the authorization badges from
  `打・可用` to `打 ✓` (full wording preserved in `aria-label`, so availability is never carried
  by colour or glyph alone; the six badges now fit one line).

Merging the two rows recovered that space. The decision card sits at y=178 collapsed — 60px higher
than before the merge — and at y=540 expanded, fully inside the sidebar in both states.

### Settings is a complete modal, not a decorative toolbar icon

Why: the settings gear is a visible product control, so the wireframe must specify its destination and every existing settings responsibility. The optimized modal uses two columns to avoid the narrow scrolling sheet while preserving the current settings inventory.

It includes player-name privacy, auto-play availability and delay, Bot rebuild/delete controls, MCP Server status/control, cloud enablement, privacy disclosure, server URL, Keychain-backed API key, 4P/3P model selection, connection testing, and explicit effective-state feedback. The gear, `19 設定` state button, and `完成` button all navigate to or from the modal.

Tradeoff: the two-column desktop layout is an optimized macOS reference rather than a pixel copy of the current 400 × 550 SwiftUI sheet. The shipping implementation still needs a separate narrow/mobile layout.

## Constraints

- Landscape macOS app screenshot, consistent dimensions and visual language.
- The WebView placeholder remains the dominant area; decision sidebar remains on the right.
- Use exact Traditional Chinese action labels.
- Do not add new product features or marketing content.
- `prototype.html` is the source of product truth; `rendered/` contains only its canonical captures.

## Acceptance criteria

- Every listed PNG exists in this directory.
- Every PNG has a valid raster format and consistent dimensions.
- Each image visibly distinguishes its named action or state.
- The final index records generated dimensions and known fidelity limitations.

## Known fidelity limits

- The left game area is intentionally not a representation of Mahjong Soul; Naki continues to use the live WebView there.
- These files are design references, not a change to the shipping Swift UI.
- The prototype no longer displays invented inference latency; Naki currently has no corresponding UI data field.
- The listed action-state mappings were checked against repository tests, but live game-path validation remains unverified for chi variants, red-five combinations, all three kan variants, kyushu, and kita.
