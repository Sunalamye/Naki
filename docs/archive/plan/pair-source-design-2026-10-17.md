# pair-source：跨來源 msgId 配對隔離（設計，2026-10-17；第二輪修訂）

基準 main `13abe49`。改 `naki-plugins.js`；`naki-websocket.js` 只多傳一個參數（本地結案帶來源）。第二輪依 Astra 第一輪 1～7 條修訂，原文見主 repo `.swfd/logs/pair-source-review/astra-review1.md`。

## 問題

配對表 `pendingMethods` 以 (連線, msgId) 為鍵，遊戲、Naki 與插件注入共用（D22）。插件注入的號碼在 64000–65500 依序輪用，不看遊戲。握手紀錄顯示遊戲 msgId 計數器跨連線遞增，會進這個號段（`d22-naki-identity.md`）。碰撞有兩種：

- **甲：遊戲先送、注入後撞號**。遊戲 INFO#64000 未答時注入拿到 64000：
  - 注入被擋時，遊戲那筆配對被撤銷（`GG11-4` 舊版）。本地錯誤回應帶 64000 交給遊戲，遊戲可能把它當成自己 INFO 的答覆。
  - 注入沒被擋時，遊戲的 RESPONSE 先到就被當成注入回應。
- **乙：注入先送、遊戲後撞號**。遊戲的配對覆寫注入配對，注入回應被派成遊戲的方法（`PS-4` 修前實測）。

前提修正：接收路徑沒有攔下 Naki 回應的程式，D22 只標記身分與已答；`respondLocal` 以 `ws.dispatchEvent` 把本地錯誤交給遊戲（Astra 第一輪確認）。所以「改寫號碼、回來還原」擋不住遊戲層的碰撞，號碼必須在配發時避開。

## 方案

1. **遊戲送出另記**（第二輪第 2 條）。`dispatch` 在「沒有消耗者早退」之前記每條連線的遊戲送出：最後號碼 `last`，以及未答號碼集合 `inflight`。經 `sendRaw` 登記、尚未答的不算（Naki 自送與插件注入）。RESPONSE 到達或 `blockSend` 本地結案時從集合移除。不依賴 `pendingMethods`，因為後者在零消耗者時不登記，滿 256 筆會 FIFO 淘汰。
   - 每連線集合上限 256。超過時標記該連線**失準**，淘汰最舊的號碼。失準的連線關閉之前，注入一律回 `{ok:false, reason:'msgid_busy'}`。不採「擴大窗口」：被淘汰的號碼無從得知何時答覆，擴大窗口仍可能撞上。
2. **配發避號**（第一輪方案，第二輪第 1、2 條修正）。`nextPluginMsgId()` 從輪用指標往後找第一個可用號碼。下列號碼不可用：
   - 任一連線上未答的注入登記（第 1 條：跳號會提前繞回，1501 > 256 不足以證明不撞）。
   - 任一連線的遊戲未答號碼。
   - 任一連線遊戲最後號碼之後 256 個，即 `0 < (id − last) mod 65536 ≤ 256`。

   不可用號碼最多「注入 256＋每連線（未答 256＋窗口 256）」。連線數超過 2 時可能占滿 1501 個號碼，這時也回 `msgid_busy`。
3. **注入配對與遊戲分開**。注入請求不寫 `pendingMethods`，注入登記值為 `{ id, method }`。辨識注入用完整 bytes 比對（msgId＋內容），不只 msgId（第 3 條），所以注入期間同號不同內容的遊戲請求照常登記。RESPONSE 先比對注入登記，命中就以注入的方法派發，只消耗注入登記。`failSafe` 照送時同樣辨識注入，不寫 `pendingMethods`。
4. **消耗不依消耗者**（第 4 條）。零消耗者早退前，RESPONSE 先消耗同鍵注入登記；沒有注入登記才消耗遊戲配對。順序與有消耗者時相同。
5. **本地結案帶來源**（第 5 條）。`blockSend` 的判決帶 `injected`。`localResponse` 只在被擋的是注入本身時認領注入登記；遊戲被擋的本地錯誤不碰注入登記。
6. **歧義回應只觀察**（第 6 條）。注入回應抵達時，同鍵若也有遊戲配對在等，就把這個鍵標成歧義。下一則同鍵 RESPONSE 對回遊戲方法，但當成 Naki 流量：只交給宣告 `observeNakiTraffic` 的 observer，沒有 `replace`。這是保守選擇，因為兩則回應誰是誰只能靠到達順序。
7. **關閉連線**。`closed` 清該連線的配對、注入登記、歧義標記與遊戲送出紀錄（含失準）。`diagnostics().pendingInjections` 回報注入登記筆數。

## 取捨

- 不採改寫號碼：遊戲看得到所有回應，而且沒有遊戲保證不用的號段。
- 不採每鍵排隊：同一來源依序重用 msgId 時舊配對要清掉（`GG11-1b`），排隊會改變這條規則。
- 不採一次性認領：相同 bytes 的重入派發，guard-gaps Deviation 11 要求兩筆都擋（`GG4-6`）。一次性認領會讓第二筆真正的注入繞過注入退回檢查。

## 前提與未驗證（第 7 條）

窗口 256 是啟發式。碰撞是否發生取決於下列未驗證的條件，不能寫成「只有超過 256 筆才可能碰撞」：
- 遊戲計數器每次 +1、跨連線共用。只有握手片段的 live 觀測；重連、繞回點與固定步進都沒有證據。
- 注入往返期間遊戲送出的筆數。心跳頻率不能界定全部操作流量，也不能界定注入等待時間。
- 遊戲客戶端收到陌生 msgId 回應（注入回應、本地錯誤）的行為。沒有 live 證據。
- 同號兩則 RESPONSE 依送出順序抵達。

條件不成立時遊戲仍可能走到注入未答的號碼。這時同號第一則 RESPONSE 歸注入，下一則只觀察（方案 6）。

## 不做什麼

- 不改 D22 身分語意與守衛判定，不改遊戲請求的 bytes（I2），不新增外送內容。
- 不處理 Naki 自送（60000–63999）與遊戲的碰撞，屬 D22 範圍。不實作注入逾時。不改 Swift。
