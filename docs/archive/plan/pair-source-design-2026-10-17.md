# pair-source：跨來源 msgId 配對隔離（設計，2026-10-17；第三輪改為交易代號）

基準 main `13abe49`。改 `naki-plugins.js` 與 `naki-websocket.js`（送出者傳遞）。審查原文在主 repo `.swfd/logs/pair-source-review/`：第一輪 1～7 條、第二輪 8～14 條。

## 問題

配對表 `pendingMethods` 以 (連線, msgId) 為鍵，遊戲、Naki 與插件注入共用（D22）。握手紀錄顯示遊戲 msgId 計數器跨連線遞增，會進插件號段 64000–65500。碰撞有兩種：

- **甲：遊戲先送、注入後撞號**。遊戲那筆配對被注入撤銷或搶走；被擋注入的本地錯誤帶著遊戲正在等的號碼交給遊戲。
- **乙：注入先送、遊戲後撞號**。配對互相覆寫，注入回應被派成遊戲方法。

接收路徑沒有攔下 Naki 回應的程式，D22 只標記身分與已答；`respondLocal` 以 `ws.dispatchEvent` 把本地錯誤交給遊戲（Astra 第一輪確認）。所以號碼必須在配發時避開，改寫號碼無益。

## 方案

1. **注入身分＝宿主交易代號**（第三輪，取代第二輪的 bytes 比對）。
   - `ctx.sendRequest` 為每筆注入配一個不透明代號 `{ id, method }`，記進閉包內的 `WeakSet`。呼叫 `sendRaw(b64, token)`。
   - `sendRaw` 把送進 `ws.send` 的那個 buffer 記進 `WeakMap`：注入記代號，Swift 呼叫（省略第二參數）記 `'naki'`。
   - `handleMessage` 以收到的 `data` 查 `WeakMap`，把送出者帶進 `dispatch` 與 `failSafe`。
   - 插件層只問「送出者是不是存活的代號」。派發、鏈首登記、判決後提交、非大廳鏈尾、`blockSend`、`failSafe`、`localResponse` 都以此判來源，不比 msgId、不比 bytes。沒有送出者的就是遊戲。
   - 守衛例外：注入期間與注入內容相同 bytes 的重入派發，仍一併做注入退回判定（guard-gaps Deviation 11，兩筆都擋）。但配對來源看代號，遊戲那筆照常登記。
2. **注入配對與遊戲分開**。注入登記 (連線, msgId) → 代號，不寫 `pendingMethods`。RESPONSE 先比對注入登記，命中就以代號的方法派給發起插件，只消耗注入登記。注入被擋時 `blockSend` 不撤銷同鍵配對，因為那是遊戲的（第 9 條）。本地結案只在被擋的是注入本身時認領注入登記。
3. **遊戲送出另記**。每條連線記遊戲最後號碼 `last` 與未答集合 `inflight`，不論頁面上有沒有插件。
   - 遊戲＝沒有送出者，不看 D22 的 `isNakiSent`（第 8 條）。
   - 送出判決確定外送後才記（`dispatch` 包一層；派發拋錯時由 `failSafe` 照送出口記），被守衛本地擋下的不算（第 12 條）。派發已記、之後 `failSafe` 才擋的，由 `blockSend` 撤回。
   - 沒被同鍵注入登記認領的 RESPONSE 才消耗（第 8 條）。
   - 每連線未答上限 256。超過時標記該連線失準，關閉之前注入一律回 `msgid_busy`。不採擴大窗口，因為被淘汰的號碼無從得知何時答覆。
4. **配發避號**。從輪用指標往後找第一個可用號碼，跳過：
   - 任一連線的未答注入。
   - 任一連線的遊戲未答號碼。
   - 任一連線遊戲最後號碼之後 256 個。

   找不到可用號碼時回 `msgid_busy`。
5. **歧義回應只觀察**。注入回應抵達時，同鍵若也有遊戲配對在等，就把該鍵標成歧義。下一則同鍵 RESPONSE 對回遊戲方法，但當成 Naki 流量：只給 `observeNakiTraffic` observer 看，沒有 `replace`。
   - 歧義鍵超過 256 個時不淘汰，而是把有歧義鍵的連線整條標成歧義，直到連線關閉（第 11 條）。寧可全部只觀察，也不忘記。
6. **消耗不依消耗者**。零消耗者早退前：
   - RESPONSE 先消耗同鍵注入登記；沒有注入登記才消耗遊戲配對與歧義標記。
   - 三張表任一非空就處理（第 4、14 條）。
7. **關閉連線**。清掉該連線的配對、注入登記、歧義鍵、整條歧義標記與遊戲送出紀錄（含失準）。

## 已被取代的做法

- **第一輪只比 msgId**（`isInjecting`）：注入期間同號不同內容的遊戲請求失去配對（第一輪第 3 條）。
- **第二輪完整 bytes 比對**：只修好跨線同號不同內容的情況。仍有三個缺口：
  - `blockSend` 不分來源撤銷配對（第 9 條）。
  - 非大廳鏈尾漏判（第 10 條）。
  - 相同 bytes 的非守衛遊戲請求被當成注入而失去配對（第 13 條）。

  根因是「從內容推來源」：內容會被鏈改動，也會與遊戲巧合相同。改由 `sendRaw` 在送出當下綁定送出者。
- **一次性認領**：會讓相同 bytes 的重入先認領，真正的注入繞過注入退回（`GG4-6`）。

## 取捨

- 不採改寫號碼，也不採每鍵排隊（同一來源依序重用 msgId 的清除規則，`GG11-1b`）。
- 代號只活在閉包與 `WeakMap`／`WeakSet`。插件自己呼叫 `sendRaw` 傳偽造物件，不在 `WeakSet` 內，會被當成 Naki 自送，不是注入。

## 前提與未驗證

窗口 256 是啟發式。下列條件都沒有 live 證據：
- 遊戲計數器每次 +1、跨連線共用（只有握手片段的觀測），以及重連與繞回點。
- 注入往返期間遊戲送出的筆數。
- 遊戲客戶端收到陌生 msgId 回應的行為。
- 同號兩則 RESPONSE 依送出順序抵達。

不成立時遊戲仍可能走到注入未答的號碼。這時第一則回應歸注入，下一則只觀察。

## 不做什麼

不改 D22 身分語意與守衛判定，不改遊戲請求 bytes（I2），不新增外送內容。不處理 Naki 自送與遊戲的碰撞。不實作注入逾時。不改 Swift：Swift 呼叫 `sendRaw` 仍只傳一個參數。
