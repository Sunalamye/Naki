# Unity wasm heap 存取（2026-08-06 實驗）

**起因**：想把「隱藏玩家名稱」從一次性（authGame byte 覆寫）改成**動態可切換**。
先前 CLAUDE.md 記的是「JS 拿不到遊戲內部物件」——本輪把這條結論**推翻了一半**。

## 推翻的部分：heap 拿得到

| 路徑 | 結果 |
|------|------|
| `window.unityInstance` / `Module` / `SendMessage` | ❌ 全 undefined（遊戲把 instance 存在 script scope）|
| 攔 `onUnityReady` / `createUnityInstance` | ❌ 頁面用**函式宣告**定義它們，直接覆蓋我們掛的 accessor |
| **攔 `WebAssembly.instantiate*`** | ✅ **可行**——頁面覆蓋不掉的入口，wasm memory 從這裡出來 |

實作：`naki-core.js` 在 document start 包住 `WebAssembly.instantiate`／`instantiateStreaming`，
把 memory 留到 `window.__nakiWasmMemory`、`window.__nakiHeap()`（唯讀捕獲，不改參數與回傳）。
實測 heap 495 MB 可讀寫。

暱稱是標準 IL2CPP `System.String`：`[klass ptr][monitor][length int32][UTF-16 chars]`
（本次 klass ptr = 22276440）。掃 UTF-16 即可定位，改寫也成功
（4 個副本全改，重掃舊字串剩 0）。

## 沒推翻的部分：改 heap 不會改畫面

三次實驗一致，**這條路在「隱藏名字」用途上是死路**：

1. 對局中改字串 → 畫面不變（TextMeshPro 已把文字烘成 mesh，只有重新指派才重繪）
2. 對局中輪詢 407 次 → 遊戲**不會**重建暱稱字串，沒有第二次機會
3. 重載頁面 ＋ 每 250ms 搶改 → 16.4 秒（名牌建立瞬間）命中，畫面**仍是舊名字**

第 3 點是決定性的：字串建立與 TMP 烘 mesh 在**同一幀**（< 16ms）完成，輪詢永遠來不及；
就算加密到每幀也是賭同幀內的執行順序，還要付全 heap 掃描的 CPU（250ms 一次已明顯吃資源）。

**要贏過它只能在字串誕生前動手＝網路封包層**——那正是現有 `__nakiHideNames` 做的事。
繞一圈回到原點：現行實作就是這個問題的正解。

## 決策：改渲染層的 alpha，判準用畫面本身

最後成立的做法是**在 draw 時把名字那個 draw 的 `_Color` alpha 設 0**，即時生效、
即時還原、不碰協定也不碰記憶體。難的從來不是遮，是**認出哪一個 draw 是名字**。

### 試過而且失敗的判準（都留著，因為它們是「為什麼不那樣做」的證據）

| 判準 | 為什麼失敗 |
|------|-----------|
| 小 quad 的 UI shader draw | 打到的是**頭像**，名字根本不在那批 |
| 逐 draw 反查螢幕座標 | WebGL2 下 Unity 把矩陣放進 **UBO**，`getUniform` 讀不出來 |
| 「只被大批次用的貼圖」 | 同時符合好幾張圖，鎖到錯的那張 |
| 四家暱稱總字數 × 6 | **人機場直接失效**——「電腦（簡單）」由客戶端產生，封包裡沒有 |
| 每幀重算 + index 數容差 | 同一幀有兩個 132 的 draw，分不出來 |
| 連續幀穩定度 | 鎖到一閃即逝的過場 UI（1661 幀只遮到 2 次） |

還有一個**真正的病根**藏在這些失敗底下：整合進 `__nakiHighlight` 時用 `L.color`
當「是不是文字」的條件，但 3D 牌的 shader 也有 `_Tint`，於是整桌的牌都混進候選。
UI／文字的識別特徵是 **`_TextureSampleAdd`**（字型 atlas 是 alpha-only，Unity 用它
把 RGB 補成 1），少了這一格前面所有判準都在雜訊上做判斷。

### 成立的判準：幾何

名字唯一穩定的特徵不在 shader、貼圖或字數，而在**畫面**：四家分坐四方，所以遮掉
名字那個 draw 會讓變動像素「**散佈在至少 3 個象限、但總量很少**」；其他 UI 文字都
集中在一處。這與版面縮放、人數、名字長度、遊戲改版都無關。

實作是自我校準：開啟遮蔽時逐一試遮候選、`readPixels` 讀回畫面比對，選散佈最廣且
像素最少的那個。實測資料（真實對局，銅之間・四人東）：

```
ord 0: n=0                       ← 沒有可見變化
ord 1: n=3037 spread=0.94 quads=3
ord 2: n=102  spread=0.86 quads=3  ← 選中（名字）
ord 3: n=295  spread=0.41 quads=1  ← 集中一處，排除
ord 6: n=1637 spread=0.82 quads=3
```

同一套校準在人機場與真實對局各自獨立跑出同一個答案，並經截圖確認：四家名字消失，
稱號／分數／局數／手牌／按鈕／頭像全部完好。

### 兩個必要的防呆

- **象限 ≥ 3**：少了它，大廳（只有自己一個名字、集中在角落）也會選出候選並遮錯東西。
- **失效重校**：換局／重載後貼圖被重建，鎖定的目標再也不會被畫；連續 120 幀一個都
  沒遮到就重新校準，否則會**靜默不遮**——比遮錯更難發現。

`readPixels` 只在校準時跑幾幀，不能進 draw 迴圈（同步 GPU 讀回，一幀數百次會卡死），
這條有機械測試守著。

## heap 捕獲鉤子保留

唯讀、無副作用，價值在**讀**遊戲內狀態（未來要驗證 Naki 的協定層重建是否與遊戲真實
狀態一致時，這是唯一的第三方對照來源）。

## 教訓

1. 「JS 拿不到 Unity 內容」這個結論**過期了**，而我一開始是憑它回答。要先探再答，
   而且探測要覆蓋 `WebAssembly` 這種頁面改不掉的層，不能只看 `window` 掛了什麼。
2. 判準連續猜錯五次之後才想到「用畫面當判準」。**當一個特徵怎麼猜都不穩，就別再猜
   內部表示，直接量測外部可觀察的結果**——這裡的外部結果就是像素。
3. 過程中真正的病根（`_Tint` 讓牌混進候選）是靠把中間資料印出來才看見的，不是靠推理。
